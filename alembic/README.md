# Database migrations

`AUTO_CREATE_SCHEMA=true` creates tables directly from ORM metadata. That is fine
for local development, the test suite and the containerised demo, but production
deployments should use migrations so schema changes are reviewable and reversible.

## Generating the initial migration

Point `DATABASE_URL` at a database and run:

```bash
alembic revision --autogenerate -m "initial schema"
alembic upgrade head
```

`alembic/env.py` imports `app.models.database`, so every mapper is registered and
autogenerate sees the full metadata. The naming convention in `app/db/base.py`
gives constraints deterministic names, which keeps generated diffs stable.

No migration is committed here on purpose: an autogenerated revision that has
never been executed against a real PostgreSQL instance is a liability, not an
asset. Generate it against your own database and commit the reviewed result.

## Notes

- The URL is read from the `DATABASE_URL` environment variable, never from
  `alembic.ini`, so credentials stay out of version control.
- `env.py` strips the `+asyncpg` driver suffix for offline (`--sql`) mode and uses
  an async engine online, so the same URL works in both.
